이번 주 작업을 돌아보니 반복해서 만난 문제가 있었다. 화면에서는 하나의 동작처럼 보이지만, 그 동작에 필요한 준비가 서로 다른 시간에 끝난다는 점이다. 외부 SDK 다운로드, 로그인 정보 복원, 서버의 이미지 렌더링은 각각 다른 생명주기를 가진다.

이때 단순히 값이 있는지 검사하는 것만으로는 충분하지 않았다. 지금 값이 없다는 것이 실패인지, 대기 중인지, 실제로 대상이 없는 상태인지 구분해야 했다. 이번 글에서는 세 가지 수정 사례를 통해 그 경계를 어떻게 다뤘는지 정리한다. 서비스 고유의 명칭과 흐름은 일반적인 예제로 바꿨다.

<Heading type="h2"> 1.SDK가 존재하는 시점과 사용할 준비가 된 시점</Heading>

기존 구조는 외부 스크립트를 불러오는 코드와 초기화 코드가 분리되어 있었다. 초기화
시점에 전역 객체가 있으면 실행하고, 없으면 지나가는 방식이었다.

```js
// 문제 구조를 설명하기 위한 일반화된 예제
if (window.externalSdk) {
  window.externalSdk.initialize();
}
```

이 코드는 객체가 없는 경우 오류를 피할 수는 있다. 그러나 다운로드가 나중에 끝났을 때 초기화를 다시 실행할 계기는 제공하지 않는다. 로딩을 시작한 순서만 보고 준비가 끝나는 순서를 기대할 수 없다는 것이 문제였다.

수정에서는 Next.js의 스크립트 컴포넌트를 앱 진입점에 두고, onReady에 초기화를 연결했다. 초기화 함수에는 브라우저 환경 여부, 전역 SDK 존재 여부, 이미 초기화했는지를 확인하는 가드를 뒀다. 로드 실패 시에는 오류를 기록하도록 했다.

여기에 한 가지가 더 필요했다. SDK 준비 전에 로그인 정보가 복원되거나, 사용자가 로그아웃할 수 있다. 따라서 SDK 준비를 기다리는 동안 가장 최근 사용자 상태를 보관하고, 초기화가 끝나면 그 상태를 적용하도록 했다. ‘아직 전달할 상태가 없음’, ‘사용자 정보가 있음’, ‘사용자 정보를 지워야 함’을 구분하는 구조다.

여기서 모든 이벤트를 큐에 쌓지는 않았다. 현재 사용자 상태를 동기화하는 목적에는 마지막 상태가 중요하기 때문이다. 준비 전에 로그인과 로그아웃이 연달아 발생했다면, 준비 후에는 로그아웃 상태가 반영되어야 한다. 반면 각 이벤트 자체를 모두 보존해야 하는 작업이라면 이 방식 대신 별도의 이벤트 큐를 검토해야 한다.

남은 확인: 이번 정리에서는 이 변경의 코드와 호출 순서를 확인했다. 느린 네트워크에서의 실제 SDK 동작이나 로딩 실패 후 재시도까지 검증한 것은 아니다. 초기화 연결과 장애 복구는 별도의 검증 항목으로 남는다.

<Heading type="h2">
  2.로그인 정보가 없다는 이유로 곧바로 비로그인이라고 판단하지 않기
</Heading>

새로고침 직후에는 저장된 세션이 있더라도 메모리의 사용자 정보가 아직 복원되지 않았을
수 있다. 기존 흐름은 사용자 객체가 없으면 바로 로그인 화면으로 이동했다. 복원 중인
상태를 비로그인 상태와 같은 분기로 처리한 셈이다.

수정한 흐름에서는 사용자 정보가 없고 저장된 세션이 있다면, 먼저 사용자 정보 복원을 기다린다. 복원 결과를 확인한 뒤 후속 요청을 실행한다. 세션도 없는 경우에는 사용자가 하려던 동작의 입력을 보관하고 로그인으로 이동한다. 복원에 실패했을 때 후속 요청이 그대로 진행되지 않도록 하는 것도 함께 고려했다.

중복 실행 방지도 같은 맥락이었다. UI의 로딩 상태는 버튼을 비활성화하는 데 사용하고, 즉시 검사할 수 있는 ref는 연속 클릭의 진입을 막는 데 사용했다. 여러 인증 경로가 같은 후속 동작으로 합류하는 부분에서는 진행 중인 Promise를 공유하도록 했다.

```js
// 실제 소스를 복사하지 않은 개념 예제
let inFlight: Promise<void> | null = null;

function runOnceWhilePending() {
  if (inFlight) return inFlight;

  inFlight = performAction().finally(() => {
    inFlight = null;
  });

  return inFlight;
}
```

이 방식이 보장하는 범위도 구분해야 한다. 같은 실행 환경에서 겹치는 호출을 줄이는 장치이며, 다른 탭이나 새로고침 이후의 요청, 네트워크 재전송까지 막는 서버 측 멱등성을 대신하지는 않는다.

인증을 거쳐 계속되어야 하는 동작의 입력과 진행 상태는 탭 단위 저장소에 보관했다. 다만 로그인 완료와 전체 흐름 완료를 같은 것으로 취급하지 않았다. 중간 단계가 남아 있으면 후속 동작을 보류하고, 흐름의 종료 지점에서 이어가도록 분기를 정리했다.

오류 처리의 책임도 나눴다. 일부 요청은 호출한 화면이 실패 결과를 보여줘야 하는데, 공통 인터셉터가 먼저 알림이나 로그인 이동을 수행하면 처리가 겹칠 수 있었다. 요청별로 공통 오류 처리를 생략할 수 있는 옵션을 두되, 오류 자체는 reject해서 호출부로 전달하도록 했다. 이 옵션을 쓰는 호출부에는 오류를 끝까지 처리할 책임이 생긴다.

검증: 이번 초안을 작성하며 기존 인증 및 단계 전환 테스트 스크립트 두 개를 실행했고 모두 통과했다. 세션 복원 대기, 연속 클릭, 비로그인 분기, 중간 단계에서의 실행 보류, 새로고침 후 상태 복원, 실패 결과 처리 등을 확인하는 테스트다. 브라우저와 외부 인증 서비스를 연결한 E2E 테스트는 아니므로 실제 환경 전체가 검증됐다는 의미로 확대하지 않았다.

<Heading type="h2">
  3.서버 이미지 생성은 렌더링 코드와 배포 파일을 함께 봐야 한다
</Heading>

동적으로 이미지를 생성하는 작업에서는 JSX와 스타일만으로 구현이 끝나지 않았다. 이미지
렌더러가 사용할 폰트 파일을 서버에서 읽어야 했고, 그 파일이 최종 실행 환경에도 있어야
했다.

이번 구현은 폰트를 런타임 파일 시스템에서 읽는다. 이에 맞춰 다단계 Docker 빌드의 최종 이미지에 폰트와 라이선스 파일을 복사하는 설정을 추가했다. 빌더 단계에 파일이 있다는 사실과 실행 단계에서 그 파일을 읽을 수 있다는 사실을 따로 확인해야 했다.

폰트 읽기에는 진행 중인 Promise를 캐시했다. 같은 프로세스에서 요청이 겹쳐도 읽기 작업을 공유할 수 있도록 한 것이다. 읽기가 실패하면 캐시를 비워 이후 요청에서 다시 시도할 수 있게 했다. 실패한 Promise를 계속 보관하면 일시적인 오류가 이후 요청에도 반복될 수 있기 때문이다. 이 캐시는 프로세스 범위에 있으므로 여러 서버 인스턴스가 공유하는 캐시는 아니다.

응답 처리에서는 이미지 바이트 생성이 끝난 뒤 PNG의 콘텐츠 타입과 길이를 설정해 전송하도록 구성했다. 렌더링 중 실패했을 때 성공 이미지처럼 응답하는 상황을 피하려는 처리다. 성공 응답에는 캐시 정책을, 렌더링 실패 응답에는 no-store를 적용했다. 입력이 배열로 들어오는 경우를 거절하고, 텍스트를 정규화하는 처리도 함께 들어갔다.

렌더링 코드는 크기와 배경 리소스를 인자로 받는 공통 핸들러로 정리했다. 여러 출력 형태에서 입력 검증, 폰트 로딩, 실패 응답 처리를 공유하도록 한 것이다.

남은 확인: 이번 정리에서는 이미지 처리 코드와 Docker 복사 설정을 확인했다. 컨테이너를 새로 빌드해 실제 이미지 응답을 확인하거나 외부 미리보기 환경을 검증하지는 않았다. 따라서 배포 환경에서의 렌더링 성공이나 캐시 효과를 검증 결과로 주장할 수는 없다.

<Heading type="h2">이번 주에 남은 설계 관점</Heading>

세 사례 모두 기능을 호출하기 전에 무엇이 준비되어 있어야 하는지 명확히 하는 작업이었다. SDK 객체가 있다는 것과 초기화가 끝났다는 것, 사용자 객체가 없다는 것과 비로그인이라는 것, 저장소에 파일이 있다는 것과 실행 컨테이너에서 읽을 수 있다는 것은 각각 다른 상태였다.

앞으로 비동기 흐름을 설계할 때는 ‘아직 준비되지 않음’을 정상적인 상태로 먼저 표현하려 한다. 각 단계의 진입 조건과 종료 조건을 정하고, 중복 호출과 실패 처리의 책임을 배치하는 것이다. 테스트에서도 최종 성공 화면뿐 아니라 준비가 늦어지는 구간과 흐름이 합류하는 지점을 더 살펴볼 필요가 있다.

이번 수정에서 속도 개선 수치를 측정하지는 않았다. 확인할 수 있는 결과는 준비 순서와 상태 분기를 코드에 드러냈고, 일부 인증 경로를 기존 자동 테스트로 다시 확인했다는 점이다.
