<Heading type="h2">
  서버와 클라이언트의 경계, 비동기 이벤트의 경계를 다시 설계한 한 주
</Heading>

이번 주에는 이력이 있는 공개 문서를 App Router로 옮기는 작업과, 기존 이벤트 전송 경로에 새로운 SDK를 함께 연결하는 작업을 진행했다. 하나는 렌더링 구조이고 다른 하나는 비동기 전송 구조지만, 두 작업 모두 기능을 어디까지 분리할지 정하는 일이었다.

공개 본문은 주변 UI의 준비 상태 때문에 늦어지지 않아야 했다. 이벤트 전송은 어느 한 SDK의 실패 때문에 다른 전송이나 사용자 동작을 막지 않아야 했다. 이번 글에서는 실제 수정에서 선택한 경계와 검증의 한계를 정리한다. 서비스 고유 명칭과 데이터는 일반적인 표현으로 바꿨다.

<Heading type="h2">
  1.App Router 이전에서 지키려 한 것은 최초 HTML의 본문이었다
</Heading>

공개 문서를 이전할 때 페이지 파일을 옮기는 것만으로는 충분하지 않았다. 기존 공통 헤더와 푸터에는 브라우저 상태와 라우터에 의존하는 코드가 있었고, 본문까지 같은 준비 조건 아래 두면 공개 콘텐츠가 클라이언트의 준비를 기다릴 수 있었다.

이번 구현에서는 제목과 선택한 버전의 전체 본문을 Server Component에서 출력하고, 버전 선택 드롭다운은 Client Component로 나눴다. 공통 헤더와 푸터는 기존 구현을 재사용하되 본문을 그 UI의 준비 경계와 분리했다. 드롭다운에는 선택에 필요한 ID와 날짜만 전달하고, 모든 버전의 본문을 클라이언트의 상태로 복사하지 않았다.

또한 공통 UI가 기존 페이지 파일에서 스타일을 가져오던 의존을 발견했다. 필요한 스타일을 공통 소스 모듈로 옮겨 두 소비자가 공유하게 했다. 공통 컴포넌트를 가져오는 것만으로 이전 라우터의 페이지 의존까지 따라 들어오는 구조를 끊기 위한 변경이었다. 이 작업을 공통 UI 전체의 스타일 전환으로 확대하지는 않았다.

<Heading type="h3">버전 선택을 URL에 표현하기</Heading>

기존 문서는 버전 선택을 로컬 상태로 관리했다. 새 구조에서는 쿼리로 선택한 이력을 지정하고 서버가 해당 본문을 출력하도록 했다. 새로고침과 뒤로·앞으로 이동에서도 선택한 버전을 복원하기 위한 선택이다.

선택한 ID가 없거나 형식이 잘못되거나 중복 쿼리로 들어오면 기본 이력으로 돌아가도록 했다. 기본 버전을 고르면 해당 선택 쿼리를 제거하고, 다른 쿼리와 hash는 보존한다. 전환 중에는 드롭다운을 비활성화하고 진행 상태를 알리는 텍스트를 제공한다.

URL 상태를 사용하면 서버 출력과 탐색 이력을 연결할 수 있지만, 버전 변경은 서버 전환을 수반한다. 모든 본문을 미리 내려 즉시 전환하는 방식과 비교하면 클라이언트에 보관하는 데이터는 줄일 수 있는 구조인 반면, 네트워크 실패와 전환 대기를 다뤄야 한다. 이번에 실제 전송량이나 전환 지연의 전후 수치를 측정한 것은 아니다.

<Heading type="h3">요청별 HTML과 공개 데이터 캐시를 나누기</Heading>
선택 쿼리에 맞춘 HTML은 요청별로 렌더링하고, 검증된 공개 이력 데이터에는 재검증
주기를 둔 캐시를 사용했다. 캐시 키에는 API 환경과 문서 종류 등을 포함해 데이터가
섞이지 않도록 구성했다. 사용자 세션이나 HTTP 응답 객체 전체를 저장하는 대신
필요한 공개 데이터만 캐시한다.

여기서 재검증 주기는 정해진 시간마다 자동으로 문서를 게시한다는 의미가 아니다. 요청에 의해 갱신이 촉발되는 정책이므로, 갱신 지연과 실패 시 동작을 별도로 확인해야 한다.

정상 응답이지만 문서나 이력이 없는 경우와, 네트워크 장애 또는 응답 형식 오류를 구분했다. 전자는 없는 문서로 처리하고 후자는 예외로 전달한다. 장애를 빈 데이터로 바꿔 반환하면 실제로 문서가 없는 상황과 서비스 장애를 구별하기 어렵고, 정상 캐시를 잘못된 결과로 덮을 수도 있기 때문이다.

문서 ID, 날짜, 본문 등은 서버 경계에서 검증한다. 다만 값의 형식을 검증하는 것과 HTML 본문의 안전성을 검증하는 것은 다른 문제다. 이번 검증만으로 임의의 HTML이 안전하다고 주장할 수는 없다.

<Heading type="h2">
  2.이벤트 전송 경로를 늘리면서 실패와 상태를 분리하기
</Heading>

기존 이벤트 호출부를 모두 한 번에 바꾸는 대신 공통 전송 진입점과 호환 진입점을 두었다. 새 호출은 타입이 있는 이벤트 정의를 사용하고, 기존 호출은 호환 경로를 통해 이동한다. 하나의 사용자 동작에서 두 진입점을 함께 부르면 중복 전송이 생길 수 있어, 호출을 연결하는 규칙도 함께 정리했다.

기존 전송 대상에는 기존 이름과 입력을 유지하고, 새 대상에는 정의된 속성만 변환해 보내도록 분리했다. 한 대상의 규격을 맞추기 위해 원본 입력을 변경하면 다른 대상의 계약까지 바뀔 수 있기 때문이다.

속성 변환에서는 문자열을 무조건 참·거짓으로 바꾸지 않았다. 예를 들어 JavaScript의 Boolean('N')은 true다. 문자열 플래그는 허용한 표기를 명시적으로 해석하고, 숫자는 빈 문자열과 비유한 값을 걸러내도록 했다. 정의에 없는 속성은 새 전송 경로에서 제외한다. 이는 해당 경로의 범위를 제한하는 처리이며, 기존 전송까지 같은 규칙으로 정제됐다는 의미는 아니다.

<Heading type="h3">SDK 준비 전 이벤트는 무한히 쌓아두지 않기</Heading>

SDK 초기화 전에 발생한 이벤트에는 큐를 사용했다. 사용자 정보 동기화는 마지막 상태만 보관하면 되는 경우가 있지만, 개별 이벤트는 각 동작을 표현하므로 마지막 하나로 합칠 수 없다.

대신 큐 크기와 유효 시간에 상한을 두었다. 초기화가 오래 지연됐다고 아주 오래된 동작을 한꺼번에 재생하지 않도록 하고, 준비되지 않은 상태에서 메모리가 계속 늘어나는 것도 제한한다. 상한을 넘거나 만료된 이벤트는 버려질 수 있으므로 전달 누락을 허용하는 선택이다.

실제 전송에서는 계정 연결, 속성 설정, 이벤트 전송을 순서대로 기다리도록 했다. 비동기 SDK 호출을 순서만 맞춰 나열하는 것으로는 완료 순서까지 보장할 수 없기 때문이다.

<Heading type="h3">await 사이에서도 상태는 바뀔 수 있다</Heading>

큐에 넣었을 때의 사용자 상태와 실제 전송할 때의 상태가 다를 수 있다. 계정 전환이나 로그아웃 시 경계 값을 증가시키고 이전 큐를 비웠다. 이벤트에는 생성 당시 경계 값을 함께 저장하고, 대기하던 속성 설정이 끝난 후에도 다시 확인한다.

```js
// 내부 구현과 이름을 바꾼 개념 예제
const versionAtStart = currentIdentityVersion;
await applyEventContext();

if (versionAtStart !== currentIdentityVersion) return;
await sendEvent();
```

이 검사는 대기 중 상태가 바뀐 이벤트를 후속 계정에 붙여 보내는 위험을 줄이려는 장치다. 이미 SDK에 전달된 요청을 취소하거나 서버 수신까지 원자적으로 묶는 보장은 아니다.

각 전송 대상의 오류는 해당 경로에서 처리하도록 했다. 한 SDK의 실패가 다른 SDK 전송을 막지 않게 하고, 초기화 실패와 전송 실패도 기록한다. 응답을 받지 못했어도 원격에서는 이미 수신했을 수 있어 무조건 재시도하지 않는 정책을 사용했다. 중복 위험을 줄이는 대신 누락 가능성이 남는다. 정확히 한 번 전달이 필요한 요구라면 서버 멱등성이나 확인 가능한 저장 구조를 별도로 설계해야 한다.

<Heading type="h2">검증 결과와 남은 범위</Heading>

이번 초안을 작성하며 이벤트 회귀 테스트를 다시 실행했고 통과했다. SDK 호출은 가짜
구현으로 기록하며, 전송 분기, 속성 변환, 기존 입력 유지, 계정 전환 순서, 큐 상한과
만료, 전송 실패 격리, 서버 환경에서의 호출 방지, 새 경로 비활성화를 검사한다. 출력된
전송 실패 경고는 테스트가 의도적으로 주입한 실패에 따른 것이다. 실제 외부 서비스의
수신까지 확인하는 검사는 아니다.

문서 이전 작업은 별도 마이그레이션 브랜치에 있는 구현을 읽었고, 해당 체크아웃에서 문서 회귀 검사와 라우터 의존 검사도 다시 실행해 통과했다. 이 검사는 서버 본문 출력, 잘못된 응답과 빈 데이터 처리, 버전 기본값, 메타데이터, 공통 UI의 라우터 의존 경계 등을 다룬다.

이번 주에 작성된 검증 기록에는 로컬 최적화 빌드, JavaScript 차단 상태의 본문 표시, 실제 데이터 대조, 버전 탐색, 캐시 장애와 복구를 확인한 결과가 있다. 다만 여러 버전 탐색은 고정 데이터 환경으로 검증했고, 캐시 만료도 실제 주기를 기다리는 대신 만료 조건을 재현했다. 이 글을 작성하면서 그 브라우저·빌드 검증 전체를 다시 실행한 것은 아니다.

운영 배포와 다중 인스턴스의 캐시 동기화, 최소 지원 WebView, 실제 인증과 입력 복원 전 범위는 별도 확인이 필요하다. 클라이언트 JavaScript 전송량, 실행 시간, 검색 성과의 전후 수치도 이번 완료 범위에 없다. 마이그레이션 브랜치의 검증을 운영 서비스의 검증으로 확대하지 않으려 한다.

<Heading type="h2">다음 작업에도 가져갈 기준</Heading>

공개 본문과 주변 UI, 기존 전송 계약과 새 전송 계약, 계정 상태와 대기 중 이벤트는 각각 다른 수명을 가진다. 이번 주의 핵심은 그것들을 하나의 준비 상태나 하나의 오류 처리로 묶지 않는 것이었다.

경계를 나누면 처리할 상태는 늘어난다. 대신 무엇을 서버에서 먼저 보여줄지, 어떤 데이터를 캐시할지, 실패한 전송을 어디까지 감수할지, 어떤 검증이 아직 남아 있는지를 더 정확하게 설명할 수 있다. 다음 이전과 SDK 연동에서도 성공 경로뿐 아니라 경계를 통과하는 데이터와 실패의 책임부터 정리하려 한다.
