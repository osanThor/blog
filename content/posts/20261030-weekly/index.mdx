이번 주에는 재인증을 마쳐도 다시 인증 화면이 나타나는 문제를 수정하고, 상위 선택에 따라 하위 옵션을 조회하는 폼을 구현했다. 서로 다른 기능이지만 공통된 질문이 있었다. 누가 상태를 바꿔야 하며, 이전 상태는 언제까지 유효한가?

인증 상태를 컴포넌트가 나타날 때마다 변경하면 사용자가 시작하지 않은 흐름이 만들어질 수 있다. 상위 선택이 달라졌는데 하위 선택과 결과를 그대로 두면, 화면에는 서로 맞지 않는 정보가 함께 남는다. 두 작업에서 상태를 생성하고 소비하고 무효화하는 지점을 어떻게 정리했는지 돌아본다. 서비스 고유 명칭과 데이터는 일반적인 사례로 바꿨다.

<Heading type="h2">
  1.재인증 요청의 시작은 마운트가 아니라 사용자 동작이었다
</Heading>

재인증 이후에도 같은 화면이 반복되는 흐름을 살펴보니, 인증 요청을 시작했다는 표시를 안내 컴포넌트의 마운트 effect에서 기록하고 있었다. 컴포넌트가 사라질 때는 cleanup에서 그 표시를 삭제했다.

문제는 외부 인증을 마친 뒤 돌아오는 순간이었다. 콜백에서 저장한 성공 상태를 안내 컴포넌트가 다시 나타나면서 대기 상태로 덮어쓸 수 있었다. 상위 페이지는 성공을 읽어 입력 화면을 열어야 하는데, 그 전에 상태를 변경하는 다른 주체가 있었던 것이다. 화면 표시의 생명주기와 인증 요청의 생명주기가 겹쳐 있었다.

수정에서는 대기 상태 기록을 실제 로그인 버튼 처리로 옮겼다. 외부 인증으로 이동할 수 있는 분기에서 복귀 위치와 대기 상태를 먼저 저장하고 이동한다. 안내 화면을 표시하기만 하거나, 현재 환경에서 외부 인증 이동을 막고 안내를 보여주는 경우에는 요청이 시작된 것으로 기록하지 않는다. 언마운트 시 요청 표시를 지우던 effect도 제거했다.

이 변화로 상태의 의미가 분명해졌다. 대기 상태는 ‘안내 화면을 본 적이 있음’이 아니라 ‘외부 인증을 실제로 시작했음’을 나타낸다. 컴포넌트가 사라졌다는 이유만으로 진행 중인 외부 작업을 종료한 것으로 처리하지도 않는다.

<Heading type="h3">화면 이동 뒤에는 현재 분기를 종료하기</Heading>

콜백에는 또 다른 문제가 있었다. 재인증 성공 후 목적 화면으로 이동한 다음에도, 아래에 있는 다른 복귀 경로 처리 코드가 계속 실행될 수 있었다. 화면 이동은 호출한 함수의 나머지 코드를 자동으로 종료하지 않는다.

```js
// 실제 코드와 경로를 바꾼 개념 예제
if (flow === "reauthentication") {
  markCompleted();
  await navigateToDestination();
  return;
}

handleOtherReturnFlow();
```

이번 수정에서는 해당 분기의 이동을 기다리고 return하도록 했다. 이 분기에 도달했을 때 아래의 다른 복귀 처리가 이어지지 않게 한 것이다. 전체 콜백에 존재하는 모든 진입 경로의 우선순위를 새로 설계한 것은 아니므로, 다른 흐름과의 조합까지 해결됐다고 확대해서 볼 수는 없다.

<Heading type="h3">성공 표시는 한 번만 소비하기</Heading>

목적 화면에서는 성공 표시를 확인해 현재 화면의 상태를 연 뒤, 저장소의 성공 표시를 제거하도록 바꿨다. 인증 결과를 현재 진입에 사용한 뒤 다음 방문에 무기한 재사용하지 않도록 하는 처리다.

이런 클라이언트 표시는 화면 전환을 조정하는 용도다. 실제 데이터 접근 권한을 증명하는 수단으로 볼 수는 없다. 이번에 확인한 수정 범위도 화면 흐름이며, 서버의 권한 검증 전체를 검증한 것은 아니다.

다른 설계로는 중앙 흐름 관리자에 전이를 모으거나 서버가 발급한 일회성 결과를 사용하는 방식도 생각할 수 있다. 이번 변경은 기존 구조 안에서 상태를 기록하는 위치와 소비하는 위치를 좁히는 선택이었다. 저장소의 상태가 오래 남는 경우나 외부 인증 자체가 실패하는 경우는 계속 별도로 살펴볼 필요가 있다.

<Heading type="h2">
  2.연동 드롭다운은 이전 선택을 무효화하는 규칙이 필요하다
</Heading>

두 번째 작업은 ‘분류를 선택하면 해당 항목 목록을 조회하고, 항목까지 선택한 뒤 상세 조회를 실행하는 폼’이었다. 단순히 옵션을 불러오는 것 외에, 선택 간의 유효성 관계를 유지해야 했다.

상위 값을 바꾸면 하위 선택을 비우고, 이전 상세 조회 결과와 오류도 초기화하도록 했다. 하위 값만 바꿔도 이전 결과를 초기화했다. 결과의 유효성을 입력값의 유효성과 연결한 것이다. 그렇지 않으면 새 입력 옆에 이전 입력으로 얻은 결과가 표시될 수 있다.

<Heading type="h3">요청 조건과 캐시의 식별 조건을 맞추기</Heading>

하위 옵션 조회에는 선택한 상위 값을 쿼리 키에 포함했고, 상위 값이 있을 때만 요청하도록
조건을 뒀다. 서로 다른 상위 선택에 대한 목록을 구분하려는 구조다.

```js
// 서비스 명칭을 제거한 개념 예제
useQuery(["dependent-options", parentId], () => fetchOptions(parentId), {
  enabled: Boolean(parentId),
});
```

제출 가능 여부도 단순히 문자열이 비어 있지 않은지만 검사하지 않았다. 현재 옵션 목록에서 실제로 선택된 상위 항목과 하위 항목을 찾고, 하위 목록을 가져오는 중이 아니며 상세 조회도 진행 중이 아닐 때 제출할 수 있도록 했다. 버튼의 비활성화와 제출 핸들러의 조건 검사를 함께 뒀다.

조회 중에는 선택 변경을 막는 방식을 택했다. 요청 도중에도 입력을 자유롭게 바꾸도록 만들려면 요청 취소, 응답과 현재 입력의 일치 여부, 오래된 응답의 표시 방지 등을 추가로 고려해야 한다. 이번 구조는 입력을 잠그는 대신 그런 동시성 상황을 줄이는 선택이다. 다만 이를 모든 중복 요청이나 경합이 제거됐다는 보장으로 해석해서는 안 된다.

<Heading type="h3">화면의 단계는 요청 상태에서 계산하기</Heading>

미리보기는 대기, 로딩, 결과의 세 단계로 나눴다. 별도 단계 상태를 매번 갱신하는 대신 요청 진행 여부와 결과 존재 여부에서 화면 단계를 계산했다. 입력이 바뀌면 요청 결과를 초기화해 다시 대기 상태로 돌아간다.

빈 응답은 정상 결과처럼 표시하지 않고 안내 대상으로 처리했다. 목록 조회 오류와 상세 조회 오류도 화면에서 확인할 수 있도록 했다. 결과 갱신 영역에는 aria-live를, 오류 안내에는 role="alert"를 적용했다. 다만 속성이 있다는 사실만으로 실제 보조기기 사용 경험이 검증된 것은 아니다.

응답 타입에는 화면에서 사용하는 일부 필드만 선택한 타입과 null 가능성을 표현했다. 타입 정의는 코드 작성 단계에서 데이터 계약을 드러내지만, 실제 서버가 그 계약대로 응답한다는 사실까지 보증하지는 않는다. 이 차이는 연동 확인에서도 드러났다.

<Heading type="h2">3.테스트 통과와 실제 연동 성공을 구분해서 기록하기</Heading>

이번 정리를 위해 기존 재인증 테스트와 연동 폼 테스트를 각각 다시 실행했고, 두 스크립트 모두 통과했다.

재인증 테스트는 버튼을 누르기 전에는 요청 상태가 생기지 않는지, 외부 이동 시 상태가 먼저 기록되는지, 성공 분기에서 이동이 한 번만 발생하는지, 성공 표시가 소비된 뒤 새 진입에서는 다시 인증 화면을 보이는지 등을 다룬다. 자식 effect를 먼저 실행하는 상황과 effect 재실행 상황도 직접 구성해 확인한다.

폼 테스트는 제어 가능한 가짜 응답으로 상위 선택에 따른 하위 옵션, 선택 변경 시 초기화, 제출 조건, 요청 인자, 로딩과 결과 전환, 빈 데이터 안내를 확인한다. 브라우저와 실제 서버 전체를 연결하는 E2E 테스트는 아니다.

이번 주 작업 기록에는 브라우저에서 옵션 목록과 제출 활성화, 선택 변경 초기화를 확인한 내용도 있다. 하지만 상세 조회에서는 서버가 입력 검증 오류를 반환해 실제 성공 결과를 확인하지 못했다. 따라서 ‘컴포넌트 로직을 가짜 응답으로 검증했다’와 ‘실제 연동이 성공했다’를 구분해야 한다. 현재 읽은 기록만으로는 서버 측 오류의 정확한 원인이나 이후 해결 여부를 확정할 수 없다.

다음 확인은 실제 요청과 서버의 입력 계약을 대조하고, 수정된 환경에서 성공·실패 경로를 다시 실행하는 것이다. 보조기기에서의 안내, 모바일 상호작용, 외부 인증 왕복도 별도의 검증 범위로 남는다.

<Heading type="h2">이번 주에 정리한 기준</Heading>

상태를 추가할 때는 값을 어디에 저장할지에 앞서, 어떤 사건이 상태를 만들고 누가 그 상태를 소비할지부터 정해야 했다. 인증 요청은 사용자의 실제 동작이 시작하고, 복귀 결과는 목적 화면이 소비한다. 연동 폼에서는 상위 선택 변경이 하위 선택과 이전 결과의 유효성을 끝낸다.

이번 수정에서 성능 수치나 운영 오류 감소율을 측정하지는 않았다. 확인할 수 있는 변화는 상태를 변경하는 지점과 무효화하는 조건을 코드에 드러냈고, 해당 경로를 기존 회귀 테스트로 다시 확인했다는 점이다. 이후에도 성공 화면뿐 아니라 상태를 이어받고 폐기하는 경계를 중심으로 검증하려 한다.
